A day with it

Here's one ordinary day, twice. "Plain" is a setup where the rules are just text the assistant reads. "Mine" is this one. Most of what mine does is hooks. A hook is a small program Claude Code runs before or after the assistant's steps, and it can refuse a step.

  1. 09:00

    A session starts

    PlainIt starts fresh. Whatever happened overnight, it doesn't know.

    MineIt starts by reading what ran while nobody was here, and tells me: which remembered facts were deleted, which notes were placed, which branches were cleaned up.

  2. 10:30

    It finishes a fix, and asks a question on the way out

    Plain"Done, the tests pass. Shall I commit it too?" I skim it, type "sure", and something I never looked at gets committed.

    Mineask_gate.py reads the reply before it reaches me. "This reply holds a question in prose", it says, and sends it back. The question comes again as a dialog with options, and the assistant waits for my pick.

    Tested by “a closing "Shall I …?" is refused”.

  3. 11:15

    A command it wants to run is blocked

    PlainIt tries a different command that gets the same thing done. The block didn't stop anything.

    MineA block is a question for me, not an obstacle. Until I reply, every other step it tries is refused. So it has to stop and ask.

    Tested by “after a block, the next call is refused”.

  4. 13:30

    It's about to edit code

    PlainMy coding guide is in its instructions somewhere. Whether it read it today, nobody checks.

    MineThe first edit is refused until it has read the coding guide, the style guide and the guide for that language. Skimming one line of each doesn't count.

    Tested by “a Python edit with nothing read is refused, naming the three files to read”.

  5. 14:00

    It changes some code

    PlainThe tests pass, so it's done. Whether those tests would notice a bug is anyone's guess.

    MineBefore it can commit, change_gate.py plants small bugs, called mutants, on every line it changed, like turning < into <=. Every mutant has to make a test fail, and no function can grow too tangled to follow. Loosening a check to get past it isn't allowed. The mutants run side by side, one per core, so a big change no longer waits on them one at a time.

    Tested by “a self-test that misses the boundary lets a mutant live”, and “a red gate commits nothing”.

  6. 15:00

    It answers me

    PlainIt sends what it wrote.

    MineIt's told to audit the answer first: read it again as a critic and look for holes, shortcuts and claims with no evidence behind them. That's the instruction. But no hook enforces it, so sometimes it's skipped.

  7. 17:00

    It spots something it can't fix right now

    PlainIt mentions it once. When the window closes, it's gone.

    MineIt writes a note in the project's journal, the log where every change goes. Later, each note gets done, dropped or kept open on purpose. More on notes below.

    Tested by “ten entries written at once all land”.

  8. 18:30

    I close the session

    PlainThat's it.

    MineWork carries on without me. Each note becomes a rule, a script, a fact or a ticket, or stays open. Branches whose work has merged are deleted. And this page is published again from my setup, but not if anything in it looks like a key, a token or a real email.

    Tested by “open PR → keep”, and “a GitHub token is refused”.

  9. 04:30

    Nobody's here

    PlainIt once noted that releases go out from a branch called release. Someone renamed the branch. Tomorrow it says the old name, with confidence.

    MineEvery remembered fact comes with a command that checks it. Each night they all run again, and a fact its check contradicts is deleted. A check that gets no answer deletes nothing.

    Tested by “a contradicted fact is deleted”, and “a check that got no answer deletes nothing”.

  10. 09:00

    ↺ The next session starts by reading all of it. That's the loop: each night feeds the next morning.

Three parts I'd show a friend

Notes

Work turns up things that aren't the task at hand: a step worth a script, a rule that's missing, a bug in someone else's corner. The assistant doesn't stop for them, and it doesn't let them go either. It writes each one down as a note, with one command.

Every note lives the same life. The next session opens by showing me how many are open, and the three oldest. Then I go through them: do it, drop it, or keep it open. A note I mark "do" turns into something that lasts: a checked fact, a rule, a script, a setting or a ticket. If I close a session with notes still open, it places them on its own.

So something I noticed on Tuesday is still there on Friday, until I decide what it is. I really like this one.

Tested by “each note is its own line, carrying a minted id”, and “a note placed as a memory fact records which fact”.

The audit

Before an answer reaches me, the assistant is told to read it again as a critic, against my credo. Every principle and every ask in it. It lists what it finds, worst first: how it works, what's wrong, and the fix. It changes nothing until I say yes to that one finding. Then it audits its own report before sending it.

It's the step that has told me a plan got too complicated, or that what it was about to build was already in the code. It's also the weak spot. It's an instruction, not a hook, so sometimes it's skipped.

The scripts

Anything done twice becomes a script. A script does the same thing every time, which an instruction doesn't. Before writing a new one, it looks for one that already does the job.

Each script carries its own tests, one line per case, named for what holds. A change goes in only when every script's tests pass and every planted bug on a changed line is caught. While this page was being built, the gate turned back several commits until their tests were fixed.

Tested by “a red gate commits nothing”.

Where it comes from

All of this grows from one short file, my credo: who I am and how I work. It loads into every session before anything else. Its mission is one line, “Build simple systems people can trust.”

It tells the assistant how to work: correct first, then simple, with no technical debt and no hacks, find the cause rather than the symptom, and claim nothing without evidence. Four principles decide the rest, and each one became something in the day above:

Checking matters more than storing.
So every remembered fact carries the command that checks it, and every script carries its own tests.
Removing is generous, not violent.
So a fact that fails its check is deleted, not flagged. A claim on this page that fails is struck out in front of you.
Point, don't copy.
So this page copies nothing. It reads the files it talks about, while you watch.
Never get ahead of the evidence.
So every check has three answers: holds, doesn't hold, and couldn't tell. "Couldn't tell" never deletes anything.

An instruction can be forgotten. That's why most of the day above is code.

Don't take my word for it

Every claim on this page names a file and the exact words that file should hold. Your browser fetched those files when the page loaded, and marks each claim with what it found ✓ holds. Press a mark to see the line. A ✓ tested mark also means GitHub's last run printed "ok" for that very test case.

Made for one person

This setup fits one person: me. My rules, my repos, my habits. It says no in exactly the places I tend to slip, and that's why it works for me.

You won't want all of it. But the patterns travel, it's all MIT-licensed, and none of it needs the rest. Good places to start:

  • credo.md. You could write your own. One line in your CLAUDE.md, @~/.claude/credo.md, loads it into every session.
  • ask_gate.py. If you've ever answered "sure" to a question you didn't read, this is the one. It's a Stop hook; settings.json shows how it's wired.
  • git_fact.sh. The idea behind the memory: a fact is only worth keeping with a command that can prove it wrong.

What it can't do yet

  • The audit is the one step no code enforces. It happens when the assistant remembers to do it.
  • Nothing measures the outcome yet. The tests show each part does what it says. Nothing shows yet that the whole makes my work better than a plain setup would.
  • Two sessions working in the same folder can trip over each other. Each one commits only the files it changed, but one can still find the other's half-finished edit in its way.
  • The 04:30 check only runs while I'm logged in. A missed night runs at my next login.
  • A ✓ holds mark means the file has the words the claim quotes. That's all it means. A ✓ tested mark means GitHub ran that exact test, and it passed. That's why each step of the day names its test, where it has one.
  • The complexity limit now covers shell scripts too. Both checks look only at the lines a change touches. Older code gets checked the next time someone edits it, and some older shell functions are still above the limit.
