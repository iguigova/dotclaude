What this is

Claude Code is Anthropic's AI assistant for programming. It works in a terminal: it reads code, runs commands and makes changes. One conversation with it is a session, and each request with its reply is a turn.

It takes its instructions from a folder, ~/.claude. For most people that folder is a page of instructions. The assistant reads them at the start. Deep into a long task, it starts to forget them. Mine is a small codebase: … scripts, each with its own tests. Some of them are hooks: small programs Claude Code runs around every step the assistant takes. A hook can refuse that step.

An assistant is only as useful as you can trust it. Most setups chase that by remembering more. This one gets it by checking more. Each claim on this page names a file and the words it should hold. Press any mark to see the line your browser found.

Where it comes from

Everything here grows from one short file, a credo: who I am and how I work. It loads into every session before anything else. Its mission is one line, “Build simple systems people can trust.”

It tells the assistant how to work: correct first, then simple, with no technical debt and no hacks, find the cause rather than the symptom, and claim nothing without evidence. Four principles decide the rest, and each one became a mechanism:

Checking matters more than storing.
So every remembered fact carries the command that checks it, and every script carries its tests.
Removing is generous, not violent.
So a fact that fails its check is deleted, not flagged, and a claim here that fails is struck out in front of you.
Point, don't copy.
So this page copies nothing. It reads the files it talks about, while you watch.
Never get ahead of the evidence.
So every check has three answers: holds, doesn't hold, and couldn't tell. "Couldn't tell" never deletes anything.

But the assistant can forget an instruction. The rest of this page is the code that keeps these ones.

What sets it apart

  1. Rules are enforced, not hoped for

    A rule that matters names the script that enforces it. When that script is a hook, it runs whether the assistant remembers the rule or not. Once a call is blocked, no other tool runs until I answer.

    Tested by “after a block, the next call is refused”, and “a red gate commits nothing”.

  2. The tooling is production code

    It's a codebase, not a prompt file. Every script carries its own self-test. And a change lands only when its tests kill every mutant on the lines it touched. A mutant is a copy of the code with one small bug planted on purpose, like < turned into <=. If no test fails, the tests weren't good enough. No check is ever loosened to pass.

    Tested by “a self-test that misses the boundary lets a mutant live”, and “a missing tool fails the gate, naming the fix”.

  3. Memory that can be wrong out loud

    A fact is one claim and the command that checks it. It's written only if the check passes that day. Every night at 04:30 each fact is checked again, and one its check contradicts is deleted. A check that gets no answer deletes nothing.

    Tested by “a contradicted fact is deleted”, and “a check that got no answer deletes nothing”.

  4. Nothing noticed gets lost

    Every turn that changes something is journaled, by one writer. What a session notices but can't finish becomes a note, and every note is done, dropped or kept open on purpose.

    Tested by “ten entries written at once all land”.

  5. It keeps working while nobody watches

    When a session ends, nobody needs to be there. Each note it left becomes a rule, a script, a fact or a ticket, or stays open. Once a day, a branch whose pull request merged is deleted. And the next session starts by reading what ran while nobody was here.

    Tested by “squash-merged branch → delete”, and “open PR → keep”.

  6. Every answer is audited before it's sent

    The standing instruction is to judge each answer against the credo, for holes, hacks and debt, before it's sent. A change isn't finished while it leaves debt, and its docs ship with it.

  7. Public by construction

    This repo is published from my own setup when a session ends, and nothing reaches it if it looks like a key, a token or a real email. What you're reading is what I run.

    Tested by “a GitHub token is refused”, and “a real email is refused”.

The loop

  1. 1 · rule A rule says what to do, and anything done twice becomes a tested script.
  2. 2 · test One command runs every script's own self-test, and GitHub runs it on every push: the second line at the top is its last run.
  3. 3 · commit A change is committed only when every test passes, no function it touched is above complexity 10, and every mutant on a line it changed makes a test fail. The script never pushes it.
  4. 4 · journal Each turn that changed something gets an entry.
  5. 5 · note What a session notices becomes a note, and each note is done, dropped or kept open.

↺ And the next session starts by reading what ran while nobody was here.

Known gaps

  • The nightly timer only runs while I'm logged in, so a missed night runs at my next login, not at 04:30.
  • A claim is checked on its words alone. That shows the file says it, not that the code does it. The self-tests check the code. Each tenet above names the self-test cases that prove it.
  • A ✓ tested mark shows the case is in the script and that script's self-test passed in GitHub's last run. The run prints a count per script, not each case, so it doesn't show this one case ran.
  • No hook runs the audit. It runs because the instructions say so, which makes it the one tenet here a long turn can forget.
  • Mutation only runs on the lines a change touches, so code written before the gate has never been mutated.
  • Shell has no complexity counter, so a shell script's functions are mutated but never measured.
  • GitHub's run skips the gate, because the code was already gated on my machine before each commit. The copy GitHub tests has no change of its own to compare against.
