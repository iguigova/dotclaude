An AI assistant that has to show its work

Claude Code is an AI that writes code from a terminal. It's quick and capable, and it forgets. Deep into a long task, it loses hold of the rules I gave it. So I stopped asking it to remember. Small programs around it keep the rules instead, and they can say no.

  • …calls held

    It can't find a way around a step I blocked.

  • …changes refused

    It can't ship code whose tests would miss a bug.

A day with it

Here's one ordinary day, twice. "Plain" is a setup where the rules are just text the assistant reads. "Mine" is this one. Most of what mine does is hooks. A hook is a small program Claude Code runs before or after the assistant's steps, and it can refuse a step.

  1. 09:00

    A session starts

    PlainIt starts fresh. Whatever happened overnight, it doesn't know.

    MineIt starts by reading what ran while nobody was here, and tells me: which remembered facts were deleted, which notes were placed, which branches were cleaned up.

  2. 10:30

    It finishes a fix, and asks a question on the way out

    Plain"Done, the tests pass. Shall I commit it too?" I skim it, type "sure", and something I never looked at gets committed.

    Mineask_gate.py reads the reply before it reaches me. "This reply holds a question in prose", it says, and sends it back. The question comes again as a dialog with options, and the assistant waits for my pick.

    Tested by “a closing "Shall I …?" is refused”.

  3. 11:15

    A command it wants to run is blocked

    PlainIt tries a different command that gets the same thing done. The block didn't stop anything.

    MineA block is a question for me, not an obstacle. Until I reply, every other step it tries is refused. So it has to stop and ask.

    Tested by “after a block, the next call is refused”.

  4. 14:00

    It changes some code

    PlainThe tests pass, so it's done. Whether those tests would notice a bug is anyone's guess.

    MineBefore it can commit, change_gate.py plants small bugs, called mutants, on every line it changed, like turning < into <=. Every mutant has to make a test fail, and no function can grow too tangled to follow. Loosening a check to get past it isn't allowed.

    Tested by “a self-test that misses the boundary lets a mutant live”, and “a red gate commits nothing”.

  5. 15:00

    It answers me

    PlainIt sends what it wrote.

    MineIt's told to audit the answer first: read it again as a critic and look for holes, shortcuts and claims with no evidence behind them. That's the instruction. But no hook enforces it, so sometimes it's skipped.

  6. 17:00

    It spots something it can't fix right now

    PlainIt mentions it once. When the window closes, it's gone.

    MineIt writes a note in the project's journal, the log where every change goes. Later, each note gets done, dropped or kept open on purpose.

    Tested by “ten entries written at once all land”.

  7. 18:30

    I close the session

    PlainThat's it.

    MineWork carries on without me. Each note becomes a rule, a script, a fact or a ticket, or stays open. Branches whose work has merged are deleted. And this page is published again from my setup, but not if anything in it looks like a key, a token or a real email.

    Tested by “open PR → keep”, and “a GitHub token is refused”.

  8. 04:30

    Nobody's here

    PlainIt once noted that releases go out from a branch called release. Someone renamed the branch. Tomorrow it says the old name, with confidence.

    MineEvery remembered fact comes with a command that checks it. Each night they all run again, and a fact its check contradicts is deleted. A check that gets no answer deletes nothing.

    Tested by “a contradicted fact is deleted”, and “a check that got no answer deletes nothing”.

  9. 09:00

    ↺ The next session starts by reading all of it. That's the loop: each night feeds the next morning.

Where it comes from

All of this grows from one short file, my credo: who I am and how I work. It loads into every session before anything else. Its mission is one line, “Build simple systems people can trust.”

It tells the assistant how to work: correct first, then simple, with no technical debt and no hacks, find the cause rather than the symptom, and claim nothing without evidence. Four principles decide the rest, and each one became something in the day above:

Checking matters more than storing.
So every remembered fact carries the command that checks it, and every script carries its own tests.
Removing is generous, not violent.
So a fact that fails its check is deleted, not flagged. A claim on this page that fails is struck out in front of you.
Point, don't copy.
So this page copies nothing. It reads the files it talks about, while you watch.
Never get ahead of the evidence.
So every check has three answers: holds, doesn't hold, and couldn't tell. "Couldn't tell" never deletes anything.

An instruction can be forgotten. That's why most of the day above is code.

Take a piece

It's all MIT-licensed, and none of it needs the rest. Good places to start:

  • credo.md. You could write your own. One line in your CLAUDE.md, @~/.claude/credo.md, loads it into every session.
  • ask_gate.py. If you've ever answered "sure" to a question you didn't read, this is the one. It's a Stop hook; settings.json shows how it's wired.
  • git_fact.sh. The idea behind the memory: a fact is only worth keeping with a command that can prove it wrong.
  • usage_snapshot.py. It works on your own transcripts too, if you'd like to see what your setup actually does.

What it can't do yet

  • The audit at 15:00 is the one step no code enforces. It happens when the assistant remembers to do it.
  • The 04:30 check only runs while I'm logged in. A missed night runs at my next login.
  • A ✓ shows that a file says something. Only the tests show the code does it, which is why the day above names a test for each step it can.
